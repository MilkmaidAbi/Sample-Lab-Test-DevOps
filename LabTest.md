## Part B: Python programming (35 marks)

Your company is building a **Smart Greenhouse Monitor**. Sensors in three zones (**A, B, C**) log temperature (°C), humidity (%) and soil moisture (%). `readings.csv` is loaded into the application as a **list of dictionaries**, one per row, with the keys
`reading_id, zone, temperature, humidity, soil_moisture`.

1. Create and switch to a new branch **`feature/requirements`**. All Part B commits go on this branch.
2. Study the existing code in `greenhouse.py`, then implement the requirements in Table 1 in the function stubs provided.

### Table 1: requirements

| ID | Requirement | Python function |
|---|---|---|
| **REQ-01** | When the user selects Option 6 "Display readings by zone", the function shall **return a list** of all reading dictionaries whose zone matches `zone`. Matching shall **ignore upper/lower case** and any **spaces before or after** the zone entered (e.g. `" b "` matches zone `B`). The original order shall be kept. If no reading matches, return an **empty list**. | `get_readings_by_zone(readings, zone)` |
| **REQ-02** | When the user selects Option 2 "Display zone statistics", the function shall return a **dictionary** with exactly the keys `"count"`, `"min"`, `"max"`, `"average"` describing the **temperature** of all readings in that zone (same matching rules as REQ-01). `min`, `max` and `average` shall be numbers; `average` shall be **rounded to 2 decimal places**. If the zone has no readings, return **`None`**. | `calc_zone_statistics(readings, zone)` |
| **REQ-03** | When the user selects Option 3 "Display hottest reading", the function shall return the reading **dictionary** with the **highest temperature**. If two or more readings share the highest temperature, return the one that appears **first** in the list. If the list is empty, return **`None`**. | `get_hottest_reading(readings)` |
| **REQ-04** | (a) The function `classify_reading` shall return the alert level of one reading as a string, using Table 2. (b) When the user selects Option 4 "Display alert summary", `get_alert_summary` shall return a **dictionary** `{"CRITICAL": n, "WARNING": n, "NORMAL": n}` counting the readings at each level. **All three keys shall always be present**, even when a count is 0 (including for an empty list). | `classify_reading(reading)`<br>`get_alert_summary(readings)` |
| **REQ-05** | The function shall validate a new reading and, if valid, **append** it to `readings`. The parameters may be strings (typed by the user) or numbers. Checks are done **in this order** and the **first** failing check's code is returned:<br>**1**: the zone (spaces removed, case ignored) is not `A`, `B` or `C`<br>**2**: any of temperature, humidity or soil moisture is not a valid number (e.g. `"hot"`, `""`)<br>**3**: humidity or soil moisture is outside **0 to 100 inclusive**<br>**0**: valid. The new reading is appended as a dictionary with the same 5 keys. The zone is stored in **uppercase**; the other values are stored as **strings** with surrounding spaces removed (same format as the CSV rows). `reading_id` is `"R"` followed by **3 digits**, equal to the **highest existing ID number + 1** (`"R013"` for the given CSV, `"R001"` for an empty list).<br>Nothing is appended when the code is 1, 2 or 3. | `add_reading(readings, zone, temperature, humidity, soil_moisture)` |
| **REQ-06** | Menu (`display_main_menu`):<br>(a) Option 5 "Add new reading" shall prompt, in this order, `Zone = `, `Temperature = `, `Humidity = `, `Soil moisture = `, call `add_reading()` and print **exactly**: code 0 → `Reading added: <new ID>` · 1 → `Error: invalid zone` · 2 → `Error: values must be numeric` · 3 → `Error: humidity and soil moisture must be 0-100`<br>(b) both `Q` and `q` shall quit<br>(c) any other input shall print `Invalid option` and show the menu again.<br>*(REQ-06 is checked by running the app, not by PyTest.)* | `display_main_menu(readings)` |

### Table 2: alert levels (REQ-04)

| Level | Condition |
|---|---|
| `CRITICAL` | temperature **≥ 35.0** **or** soil_moisture **< 20** |
| `WARNING` | not CRITICAL, **and** (temperature **≥ 30.0** **or** soil_moisture **< 35**) |
| `NORMAL` | everything else |

### Sample console output (with the given `readings.csv`)
```
Enter selection => 2
Zone = a
Count = 4
Min = 9.5
Max = 30.0
Average = 23.25

Enter selection => 4
CRITICAL = 3
WARNING = 4
NORMAL = 5

Enter selection => 5
Zone =  c
Temperature = 24.5
Humidity = 55
Soil moisture = 41
Reading added: R013
```

> **Hints** (these are allowed in the real test, so learn them)
> - `float("hot")` raises `ValueError`. Use `try:` / `except ValueError:` to detect a non-number.
> - `"R012"[1:]` → `"012"` · `int("012")` → `12` · `str(13).zfill(3)` → `"013"`
> - Every value read from the CSV is a **string**.

3. Commit your work on the branch using **these three exact messages, in this order** (one commit each):
   **`Implement REQ-01 and REQ-02`** → **`Implement REQ-03 and REQ-04`** → **`Implement REQ-05 and REQ-06`**
4. Merge `feature/requirements` into `main`. Push `main` **and** the branch.
5. Create an annotated tag **`v1.0`** with the message **`Requirements implemented`** and push the tag.

1. **DEF-02, test first.** Write `test_get_reading_by_id()` so that it **fails** on the given code because of DEF-02. Commit **only the test** with the message **`Add failing test for DEF-02`**.
2. Fix both defects in `greenhouse.py`. Do **not** change `test_convert_to_fahrenheit()`. Commit with the message **`Fix DEF-01 and DEF-02`**.
3. In `test_greenhouse.py`, implement the PyTest cases in Table 3. Every test must cover the **normal** case, the **empty / not found** case, and **every boundary** stated in its requirement. Build your own test data in the same format as the CSV rows (strings).

### Table 3: PyTest functions

| PyTest function | Tests |
|---|---|
| `test_get_readings_by_zone()` | REQ-01 |
| `test_calc_zone_statistics()` | REQ-02 |
| `test_get_hottest_reading()` | REQ-03 (including the tie rule) |
